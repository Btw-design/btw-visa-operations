# Apply the OCR update to the current Hostinger site

For the newer server-side PaddleOCR option, use [PADDLE-OCR.md](PADDLE-OCR.md). The static-file instructions below update the browser reader; they do not activate a Python OCR backend.

The live site serves frontend files directly at the website root. The current release must be deployed as the contents of `dist/`, including its `index.html`, JavaScript modules, and `ocr-release.json`. Keep the existing vendor and brand folders. Merge the supplied `.htaccess` cache-header block with any existing rules. Updating just the earlier four OCR files is insufficient because this release versions the complete module graph.

Download the current repository ZIP from GitHub and extract it. In Hostinger File Manager, open the folder containing the live `app.js` (normally `public_html`) and copy the contents of the extracted `dist/` folder there. Avoid adding an extra enclosing directory. Use `dist/index.html`, not the repository-root launcher `index.html`. Clear Hostinger/CDN cache and hard-refresh the browser with Ctrl+F5. Confirm both PCs show the same passport reader version before reading the same files again. Existing PDF/OCR language assets do not need replacement if their contents are unchanged.

The update reads visual labels without requiring an exact P<IND line. It associates dates with labels, validates MRZ field check digits, leaves contradictory dates empty, retains more image detail, and retries weak reads with enhanced contrast and an MRZ pass. Missing critical fields are listed for review. Processing stays in the browser, with no external OCR or OpenAI API.

Validation: 42 regression checks and a synthetic-image test through the actual English OCR engine. One supplied low-resolution passport image was tested locally; the recovered fields matched, and names and the issue date remained unreadable reliably. Other customer scans still need testing. Ten simultaneous-user capacity has not been established. This frontend update does not add staff authentication to a site that is served statically.


The second update adds four-times scaling for small images and position-specific letter/digit repair with mandatory field check digits. All four JavaScript files must be uploaded together. In the supplied low-resolution sample, the number, birth date, expiry, sex, nationality, issuing country and document type were recovered correctly; names and issue date still required manual completion. A larger original image remains recommended.

The current update accepts both one-letter/seven-digit and two-letter/six-digit Indian passport numbers. It reads English labels alongside Hindi text, separates old-passport continuation blocks from current identity fields, and separates recognized Indian birth states from the birth city. Birth country is inferred from a recognized Indian state, not from nationality. Contradictions between printed identity fields and checksum-validated MRZ fields are left blank for review.

OCR retries now include missing Indian place fields. When front and address pages are stacked in one image, retries search an additional MRZ band near the middle and a printed-details crop on the upper page. That crop retains the passport-number header so alternate printed fields can be matched against the same identity. Printed birth and issue places can be recovered from another pass only when its passport number, birth date and expiry agree.

Validation for this update: 36 passport regression checks, 13 workflow checks and JavaScript syntax checks passed. A synthetic stacked-page image processed with the actual English Tesseract.js engine recovered all 14 target fields. A transcription of the newly supplied sample also matched all 14 target fields and excluded its old-passport details; the newly supplied image pixels have not been tested locally. The earlier low-resolution image remains a separate accuracy check. These checks do not establish 100% accuracy on customer scans. Review the values after deploying the four JavaScript files to the live site.

## Consistency update

A single disagreement between a printed date and the MRZ previously cleared nearly every identity field. When the passport number agrees, a checksum-verified MRZ date now supplies that date and creates an explicit review warning, preserving the other matching fields. Different passport numbers still prevent name/issue-date mixing. A conflicting name affects that name, rather than clearing the other details.

Run `npm run build:release` after changing application code. It adds content hashes to the complete module import graph and both HTML entry pages. `dist/ocr-release.json` records the release hashes; the page header shows the passport reader version. The Node server revalidates HTML/JavaScript/JSON, and `dist/.htaccess` supplies equivalent cache headers for compatible static hosting.

This release requires the updated `dist/index.html`, every updated JavaScript module (including `address.js`), and `ocr-release.json` together. Copy the contents of `dist/` into the live website root, retaining the vendor and brand folders. Merge the supplied `.htaccess` cache-header block into any existing hosting configuration instead of deleting its existing rules. Purge Hostinger/CDN cache once after deployment and refresh both PCs. Both PCs must display the same passport reader version before comparing the exact same files. Updating only the earlier four OCR files is no longer sufficient.

For stronger consistency across PCs, use one server-side OCR pipeline with a pinned engine/model and preprocessing version. The browser should upload original file bytes rather than its own resized canvas. This changes the current browser-only document processing design and requires suitable backend hosting; it has not been deployed by this update. Server OCR improves control over processing but does not guarantee complete extraction from every scan. A separate accuracy test set is still needed.

Validation for the consistency release: 39 passport checks, 3 release/versioning checks and 13 workflow checks passed. In Chromium, the supplied low-resolution image and a synthetic stacked-page image each returned identical form values at normal CPU speed/DPR 1 and throttled CPU/DPR 2. Scalar, SIMD and relaxed-SIMD engines also returned identical extracted results for the supplied low-resolution image, so engine selection was not established as its cause. These local checks do not reproduce the user's exact two physical PCs or both supplied passport images, and they do not establish live-site deployment.
